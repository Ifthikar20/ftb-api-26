## P1 — Quality / retrieval improvements

- [ ] Reranker pass: take top-20 from cosine, run a Haiku rerank, keep top-5. Materially better at de-duping near-paraphrases
- [ ] Hybrid search: combine BM25 (Postgres `to_tsvector`) with cosine via reciprocal rank fusion. Helps for keyword-heavy queries that embeddings handle poorly
- [ ] Per-chunk metadata: detected entities (products, competitors), so we can boost/filter retrieval by entity rather than only by `kind`
- [ ] Track which chunks were actually used per audit + whether the brand was mentioned. Feeds a future ranker that learns chunk usefulness

## P2 — Infrastructure / scale

- [ ] Migrate embeddings from `JSONField` to `pgvector` once any single user has > 10K chunks. `retrieve()` is the only call site that touches embeddings, so the swap is local
- [ ] Add HNSW index on the pgvector column when migrated
- [ ] Background recrawl job: re-fetch sources older than N days and re-ingest if `content_hash` changed
- [ ] Streaming ingest for very large sites — current crawler is bounded at 12 pages; raise + paginate

## P2 — Embedding model upgrades

## Known limitations (worth documenting in CLAUDE.md or pinning to the PR)

- The hash-based fallback embedder is **not semantic**. Tests use it because they don't have an API key, but production must run with `OPENAI_API_KEY` set.
- Crawler obeys `robots.txt`? **No** — currently fetches whatever the user provides. Add `urllib.robotparser` check in `crawler.crawl_site` before broader rollout.
- Audit-context self-ingest can produce near-duplicate chunks across audits if the underlying website hasn't changed. The content-hash check covers identical text, not near-duplicates. Reranker pass (P1) would absorb this.
- No cross-tenant query isolation at the DB level — relies on application-layer scope on `(user, website)`. A pgvector migration should keep this discipline.
